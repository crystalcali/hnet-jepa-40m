# H-Net-JEPA-40M — план реализации

Целевая платформа — NVIDIA DGX Spark (ARM64, GB10). Этот план фиксирует согласованные поправки к исходному ТЗ v1.0. В перечисленных пунктах применять формулировки ниже. После апрува включить их в единый `SPEC.md` до начала реализации. Код и запуски на Spark начинаются после апрува.

## Поправки к ТЗ

1. **Dynamics JEPA (§5.4).** Для позиции `k = 1…8` сопоставлять цель из `M ≥ 1` готовых стадий по правилу `j(k) = ceil(k × M / 8)`. Для случайно выбранного `K` считать loss по итерациям `1…K`. Это сохраняет одну и ту же цель для `h_k` при любом `K ≥ k`. Целевой вектор — среднее валидных латентов `Z3` размерности 512 из отдельного кодирования целевого блока или накопленной трассы. CE на готовом ответе применяется к `h_K` при любом тренировочном `K`. Проверить инвариантность индексов и формы в тестах, включая `M=1`, `M>8` и `K=1,8`.
2. **Конец промпта в режиме B (§3, §4).** Завершать входной промпт служебным EOS и принудительно оставлять его позицию на всех трёх уровнях сжатия. Учитывать EOS в общем лимите контекста из §4. Принуждение действует только при кодировании промпта в режиме B. Проверить, что изменение суффикса до EOS влияет на память даже при фиксированных остальных границах, а изменение target оставляет память неизменной.
3. **Фактическое сжатие (§3).** Для `L_ratio` и `L_anti` использовать число hard-границ на прямом проходе, с градиентом через вероятности на обучаемых позициях. Обязательные границы считать константами, padding исключать. Начальные пороги трёх роутеров калибровать на train под ориентиры 4×/3×/3×. На фиксированной валидации измерять фактический `sum(T0) / sum(T3)`, распределение hard ratios по уровням, языкам и доменам, а также отклонение soft-оценки. Допустимый диапазон вокруг 36× зафиксировать на pilot/dev до полного эксперимента.
4. **Выборка для SIGReg (§5.5, §7.2).** На каждом шаге оптимизатора объединять валидные представления нескольких микробатчей с сохранением градиента. Считать SIGReg в FP32 один раз на совместной выборке из не менее 256 векторов на уровень с равными весами RU и EN. Если pooled-представлений мало, использовать предусмотренную ТЗ выборку локальных латентов из разных документов. Если после объединения выборка мала, пропустить соответствующий член с явным флагом. Логировать число векторов и документов по уровням и долю шагов, где SIGReg сработал. Измерить дополнительную память до пилота.
5. **Общая экспозиция для A/B/C (§7–8).** Для пилота и полного эксперимента зафиксировать общий детерминированный порядок базовых обучающих пар и границы curriculum по накопленным BPE-эквивалентным токенам. Доли прогресса в расписании весов и активации рекуррентности привязать к тем же отметкам экспозиции. Одну пару считать один раз за базовую подачу. Дополнительные вычисления, включая auxiliary decodes и повторное кодирование, учитывать отдельно. Сравнивать достигнутые контрольные точки по экспозиции, вычислениям и времени. Лимит полного обучения каждой модели — 72 часа вместе с валидацией и чекпоинтами.
6. **Политика корпуса (§0, §6).** Разрешить готовые опубликованные параллельные RU–EN пары, включая опубликованные синтетические переводы и задачи, если они проходят проверку происхождения, лицензии, парности и загрязнения тестов. В рамках проекта запрещено создавать новые обучающие тексты, переводы и задачи. Диагностические фикстуры и генератор оценочных задач хранятся отдельно от обучающего корпуса.

## Порядок работ после апрува

1. Собрать `SPEC.md`, конфигурации и CPU-reference. Проверить причинность и градиенты роутеров, целевые формы, поведение режима B и фактический подсчёт параметров. Лимит модели C — 40 млн уникальных обучаемых параметров с учётом вспомогательных голов.
2. Проверить на DGX Spark PyTorch/CUDA, BF16, прямой и обратный проход Mamba-2 и causal-conv, параметры SDPA и пути установки зависимостей. Замерить память и скорость с активными objectives. При недоступности GitHub со Spark использовать перенос Git bundle и зависимостей через существующий авторизованный канал.
3. Провести аудит RU–EN корпуса и подготовить пилот до 30 млн BPE-эквивалентных токенов. Отдельно показать дефициты по квотам, пригодные трассы, локальные выравнивания и возможные пересечения с тестами. Подкорпус меньшего объёма считать диагностическим.
4. Проверить все функции потерь, возобновление с чекпоинта и K-sweep, затем провести пилот A/B/C при достаточном корпусе и работоспособных CUDA-ядрах. Оформить метрики, отчёт по тестам, README с командами для Spark и локальный интерфейс диагностики согласно ТЗ.
5. После пилота оценить доступный объём данных и реальный бюджет полного эксперимента. Полное обучение каждой модели запускается только отдельной командой по явному решению пользователя.
